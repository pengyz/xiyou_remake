## §0 结论（TL;DR）

1. 求解目标**不是单一标量**，而是两层：**硬门槛（可行性）** → **软收益（ROI）**。
2. 分段求解**不是新架构**——`solve_local`（单层）+ `solve_global`（层间拼接）已是现状；缺的是**段间价值函数**与**门槛表**。
3. 硬门槛必须**数据化**（`data/solver/gates.json`），定图与随机生成**共用一份**；禁止在求解器代码里 `if item == 23`。
4. ROI 的记账单位取**血量**；段间汇率 `λ(f)` 由该段商店/丹药的兑换率估出，随 `floorTier` 递增 —— 这是"钱越高层越划算"的机制来源，不是直觉。
5. 随机地图**保留分层**（分层是机制属性，不是地图属性），但四个前提失效：静态门槛表、界内无解判据、差分裁判、离线性能假设。

## §1 两类目标：判据是"缺了会怎样"

| 类别 | 定义 | 缺失后果 | 求解方式 |
|---|---|---|---|
| **硬门槛（gating）** | 没有它则该段/后续**不可通关**（可行性门） | **无解** | 段内 must-collect 子目标：先解可达性，再解最小血量代价 |
| **软收益（ROI）** | 有了更好，没有也能过 | 可解但更贵（血/时间/后续成本上升） | 纳入段间价值函数做权衡 |

**判定准则**：某项是否可"选择不拿"。不可 ⇒ 硬门槛；可 ⇒ 软收益。

典型归类（证据见 §2）：

|---|---|---|

| 捆仙绳 24 / 乌金棍 79 / 银缕锁甲 80 | **硬门槛**（打杨戬门槛之一） | `scene.rs:2602` 原文 |

## §4 分段求解的形式化

### §4.1 段（segment）

段 = 连续楼层区间 `[f_a, f_b]`，切分依据（优先级从高到低）：

1. **`floorTier` 边界**（10/20/30/40/50）——增益断崖点；
2. **硬门槛位置**（必须在该段内可达并获取）；
3. **商店位置**（经济学节点）。

不做等距切分。

### §4.2 段间接口（boundary state）

```
B = { floor, pos, hp, atk, def, gold, keys(y/b/r), item_types, flags }
```

与 `solve_global::State`（`solve_global.rs:100-110`）一致，**新增语义**是：`atk/def/gold/keys` 参与支配与估值。

### §4.3 价值函数（ROI 的可计算形式）

```
V(B) = hp + λ(f)·gold + Σ_keys μ(c)·count + Σ_items ν(i) − Risk(f, B)
```

- `λ(f)`：**血量/金币汇率**，定义为"第 f 层段 1 金最多能换回的期望血量"。
  可计算上界 = `max(血药兑换率, 丹药边际血量价值)`，用 §2.2 的 tier 与实际商店货单估；
- `μ(c)`：钥匙期权价值（约束型，取"下一门槛缺 1 把"的边际成本，而非线性累加）；
- `ν(i)`：装备/被动的边际减损（由 `predict_battle_hp_loss` 对后续敌群差分求得）；
- `Risk(f,B)`：前瞻下界（landmark）修正项，用于惩罚"钱不够买下一段必需的钥匙"的状态。

`λ(f) ∝ floorTier(f)` 是**由机制导出的**，不是可调参数——**禁止**为了"凑出解"调 λ。

### §4.4 最优性口径

分段求解在**接口维度完备**时是精确的（段间无隐藏耦合）；否则是近似，必须在报告里标注：

> 近似来源：段界处置信集压缩 / 贪心闭包决策 / λ(f) 的估计误差。

## §5 门槛表 `data/solver/gates.json`（草案）

**双消费者**：定图求解器（真实门槛）+ 随机生成器（放置约束）。**禁止**代码内硬编码。

```jsonc
{
  "schema_version": 1,
  "gates": [
    { "id": "taigong", "kind": "hard", "item": 23,
      "requires": [17, 18],                 // 前置：拆墙手段（任一）
      "floors": { "min": 15 },              // 定图事实：藏在 15 楼以上墙内
      "unlocks": ["battle:tian_shen_li_shi", "battle:ju_ling_shen"],
      "evidence": ["scene.rs:2596", "combat.rs:96"] },
    { "id": "yangjian", "kind": "hard", "any_of": [24, 79, 80],
      "unlocks": ["battle:yang_jian"],
      "evidence": ["scene.rs:2602"] },
    { "id": "lucky_coin", "kind": "soft", "item": 25,
      "effect": "kill_gold_x2", "valuation": "early_is_better" },
    { "id": "golden_key", "kind": "hard_precursor", "item": 85,
      "effect": "remove_all_type:1", "synergy": "yellow_key_to_gold" }
  ]
}
```

字段约定：
- `kind ∈ {hard, hard_precursor, soft, constraint}`；
- `requires/any_of` = 前置物品集合（用于生成器的"必须早于"约束）；
- `floors` = 定图事实区间；随机地图下作为**生成区间约束**；
- `evidence` = 必填，指向 A/B 级证据；缺证据的门槛**不得**进表（只能进 findings 假设区）。

## §6 随机地图扩展缝（用户 m00182 提出，分层保留）

### §6.1 保留的部分（机制层，与地图无关）

- 换层 = `Exit#1` 楼梯边，实体/脚本/flags 逐层重置（引擎语义）；
- `floor_tier` 是楼层号纯函数；
- `solve_local` 输入为 `LevelSpec`（`solve_local.rs:51,67`），**不读磁盘、不认硬编码楼层** ⇒ 已 map-agnostic；
- `solve_global` 只消费 goal 列表，同样无需改。

**推翻假设的反证**：随机地图只要能产出 `LevelSpec`，求解器一行不改即可跑。

### §6.2 失效的四个前提

| # | 前提 | 随机地图下 |
|---|---|---|
| P1 | 门槛位置静态（"15 楼以上墙内"是定图事实） | 变成**生成器放置约束**（`gates.json` 的 `floors`/`requires` 即为约束源） |
| P2 | "界内无解"是结论 | 变成**实例分布**：应报"不可解率"或"构造性可解保证" |
| P3 | 差分裁判 = 参考版 Java（D3） | **随机地图无 Java 参照** ⇒ 需新裁判（不变量 + oracle 回放 + 生成证书）；属 Stage B，待用户裁定 |
| P4 | 离线一次 1e6 节点可接受 | 生成循环内反复调用 ⇒ 需 anytime + 下界，或改为"构造带 witness" |

### §6.3 建议路径：带证书生成（generate-with-witness）

生成器产出 **地图 + 可行路线 + 段预算平衡证明**，难度由预算函数反推怪物/道具/钥匙配额。
可解性由构造保证；求解器角色降为"**验 witness + 量松弛**"（有界搜索给最优差距）。

### §6.4 现在就做的低成本预留

- `LevelSpec` 增 `source: Authored | Generated { seed }`，golden/ratchet 只吃 `Authored`（防随机图污染保真基线）；
- 求解结果增 `witness` 字段（现有 `truncated` 语义可扩展）。
