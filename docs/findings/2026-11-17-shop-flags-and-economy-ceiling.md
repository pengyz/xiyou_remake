# 商店 flags 分派、幸运币缺席与 f12 经济天花板

日期：2026-11-17　工具：`cargo run -q -p game-solver --example dump_levels`（本仓新增调试工具）

## 1. 引擎侧真语义（A：`crates/game-core/src/scene.rs:2645-2745`）

`apply_merchant_offer`，购买成功后的收尾块：

```
flags & 2 != 0                       ⇒ 才会开价（否则不出购买面）
买成功：
  flags & 4 != 0  ⇒ 什么都不做（param 不清、实体不删）⇒ **可无限重复买**
  flags & 4 == 0  ⇒ param ^= 512（清开价位）
                    flags & 1 != 0 ⇒ 实体保留（走报价队列 + 浮层，此后不可再买）
                    flags & 1 == 0 ⇒ markEntityRemoved（实体消失）
```

## 3. 求解器当前模型与差异（欠近似，非错误结论）

`solve_local.rs:1611-1631` 买成功后**无条件** `ns.ents.remove(slot)`。

- 对 `flags=2` 的 2 家（f2、f37、f52 同型）：删实体正确。
- 对 `flags=3`（8 家）：实体本应保留（只是开价位清掉）⇒ 建模成删除，**但买第二次本就不行** ⇒ 无收益损失。
- 对 `flags=6`（f12 idx5、f28 idx8）：本可**无限重复买**，建模成一次性 ⇒ 少机会。

**但对 f12 红钥匙无帮助**：f12 那家可重复店卖的是「黄+1 ¤1000」（钱坑），f28 那家卖的是
「黄-1→¤+100」（在 f12 之后）。所以「红钥匙买不起」不是被 flags 分派压掉的。

## 4. 幸运币（item25）在当前数据里不可获得

`dump_levels` 全 54 层拾取实体的 ty 集合中**没有 25**；商店 AddStack 只有 13（火眼金睛）
与 19（千年月桂露）。⇒ `kill_reward` 的双倍分支在当前数据集是不可达代码。

这条直接影响 ROI 设计的前提：用户提出的「幸运金币应尽早拿以复利」在本数据集是**空集**。
若后续要让它成立，必须先找出它的真实来源（宝箱组？未导出的地图？），否则任何「早拿幸运币」
的策略建模都是对着不存在的边做优化。

## 5. f1..f12 的赏金天花板

逐层击杀赏金合计（`enemybasegold.txt` × 该层怪物数，未计双倍）：

```
f1=34  f2=200  f3=25  f4=35  f5=32  f6=57
f7=58  f8=69  f9=72  f10=102  f11=192  f12=206     累计 1082
```

观测到的 Q1 逐层金峰：f10=538、f11=718、**f12=767**。

⇒ 红钥匙要 800，累计赏金 1082 足够，**差 33 是取舍问题不是天花板**：中间在 f6（蓝钥匙 ¤50）、
f7（黄×5 ¤50）各买了 100 金；若能靠拾取而非购买过门，金就够。

## 6. 结论与下一步

1. 「界内无解」在这三条查询口径下成立，但**它不是「世界无解」**——三条查询分别最大化血量、
   最小化击杀、问最终可达性，**没有一条在问「到达 f12 时金币能否 ≥800」**。
2. 建议新增 **Q4：max gold at floor N**（`--floor 12`），把「经济可达性」变成一个可直接回答的问题；
   这也是用户 ROI 框架里「段内资源目标」的第一个可判据实例。
3. flags 分派（§3）应做但不紧急：它是欠近似清单的一项，对当前结论无影响，等 Q4 出来再定优先级。

## 7. 【同日自我更正】§5 的「金差 33」不是有效目标

用户质疑：「金>800 这个目标哪里来的？金的作用是商店消费，你的解里，会消费吗？」

答：**800 是我自己从「f12 商店红钥匙价 800」反推出来的代理目标，不是游戏目标**。
更糟的是它连必要性都不成立——红钥匙有 **6 处免费拾取**：

```
f8 (2,2)  f14 (10,1)  f34 (8,5)  f37 (7,5)  f42 (7,1)  f51 (6,2)
```

而红门最早出现在 f10（1 扇）；到 f25 才密集（6 扇），f26 4 扇，之后 f38/40/45/49/51 各 1 扇。
也就是说：**f8 那把免费红钥匙就能开 f10 的红门，f12 花 800 金买红钥匙是可选方案，不是必经**。

求解器的消费实况（Q1）：购买 583 次、买红 0 次——它确实在消费，花在蓝/黄钥匙上；
金峰值 767 是「花完之后」的余额，本身不构成任何目标。

**修正后的口径**：金无终局价值，唯一正确的问题是「通往终局的路径上，哪些门/怪是必经的，
开到那里缺什么资源」。这等价于把「金 800」换成「必经门清单 + 每扇门的钥匙来源」。
`dump_levels` 已补 DOOR 输出（`floor=N DOOR 黄|红|蓝 ty pos param`），可支撑该清单的取证。
