# 逐层累计供需对账：钥匙够不够、在哪一层会破产

> 输入=`docs/findings/mandatory-doors.md` 的必经门清单 + 逐层拾取实体；
> 输出=一条**时间轴上的钥匙序列**。命令：`cargo run --release -p game-solver -- keys`。

## 1. 口径

- **需求**：该层必经门按颜色计数（每扇门 1 把同色钥匙）。
  `全门` 模式改统计该层全部同色门——模拟「见门就开」的另一极端。
- **供给**：该层地面拾取的钥匙实体（ty=26 黄 / 27 红 / 28 蓝）。
- **结算顺序**：同层先拾取、后开门。若某层的拾取格恰在门后，该假设会偏乐观，
  属保留项（当前未逐层核实拾取点与门的拓扑先后）。
- **不含商店**：商店是「花钱换钥匙」，属可选项；对账先回答「不买够不够」。

## 2. 结果一：最小预算（只开必经门）——全程自给

| 颜色 | 全程需求 | 全程拾取 | 余额峰值 | 首次断供 |
|---|---|---|---|---|
| 黄 | 29 | 176 | **145** | 无 |
| 红 | 4 | 6 | 2 | 无 |
| 蓝 | 0 | 21 | 21 | 无 |

红钥匙的收支节奏（唯一紧张的一条线）：

```
f8  拾 +1 → 1
f10 门 -1 → 0      ← 第 1 扇红门（f10 6,9）
f14 拾 +1 → 1
f20 门 -1 → 0      ← 第 2 扇（f20 6,9）
f34 拾 +1 → 1
f40 门 -1 → 0      ← 第 3 扇（f40 6,8）
f37 拾 +1 → 1      ← f37 在 f40 之前，与 f34 同为冗余来源
f42 拾 +1 → 2
f51 拾 +1 → 3 / 门 -1 → 2   ← 第 4 扇（f51 4,4）
```

每一次消耗之前都恰好有一次供给，余量从不低于 0——**这套关卡是按「刚好够」设计的**。

## 3. 结果二：见门就开——第 1 层就破产

| 颜色 | 全程需求 | 全程拾取 | 首次断供 |
|---|---|---|---|
| 黄 | 246 | 176 | **f1**（需 7，手里 5） |
| 红 | 18 | 6 | f25 |
| 蓝 | 45 | 21 | f2 |

f1 一层就有 7 扇黄门而只有 5 把黄钥匙；f9 需要 11 黄 + 2 蓝，手里只剩 2 黄。
所以「见门就开」不是奢侈，是**立刻不可行**。

## 4. 结论

1. **钥匙预算在最小口径下完全自洽**：不买任何钥匙，全程不断供。`f7 黄×5 ¤50`
   这类商店在「能不能通关」上不是必需品，只在「想多拿支线」时才有意义。
2. **蓝钥匙一把都不必**（需求 0 / 供给 21），买蓝钥匙对通关零收益——与必经门清单一致。
3. **「够用即可」是唯一可行策略**，不是保守选择：全门口径下 1 层就破产，说明
   富余的黄钥匙（峰值 145）实际是「可选门的预算上限」，不是可以随便花的余量。
4. 断供风险最高的不是红（刚好够但每步都被设计好），而是**黄**——因为它数量大、
   分布密，任何「见黄门就开」的习惯都会立刻透支。

## 5. 保留项

- 同层「先拾取后开门」未逐层核实地形先后；若有层例外，需在 `analyze` 里加拓扑次序。
- 需求只算门，不含「开门的绕路成本」（血/怪）——那是 ROI 层的事。
- 商店供给（¤50 换 5 把黄）未纳入对账；纳入后只会让结论更宽松，不改变断供判定。
- **f49 无出发型出口**（换层靠脚本，未建模）：对账把它记入 `no_exit_floors` 并显式打印，
  不当作「该层需求为 0 所以没事」。
- 同层「先拾取后开门」仍是隐式假设，见 `2026-11-17-solver-map-vs-mechanism.md` §3。
