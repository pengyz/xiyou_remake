## 攻击点 1：弃件/留用件边界——留用件没有闭环验收判据

- **风险**：设计件 :15 说 ① 是"留用件（量产渲染层同款）"，但 §2 判据（:40-42）全部可由
  **demo 图集（弃件）**满足：d=1 恒等是硬判据，而 d>1 的验收只有"采样矩阵测试"（合成小图）
  + 用户判读 demo 截图。真实 HD 素材（量产件，:8 声明"后续另件"）到来之前，留用件的
  d>1 分支从未接触过真素材——demo 结束后留用件即以"未闭环"状态入库。
- **反例**：① 的 §1.4（:29）采样算法"待复核定夺（最近邻 vs box filter）"——留用件带着一个
  **未裁定的算法决策**入库；弃件拆除后 d>s 降采样/d<s 升采样分支 = 无真素材、无视觉闸
  （gates/cli.py:368-371 visual SKIP，`gates/visual_diff.py` 缺席亲验）、无金样覆盖的三无
  代码。量产素材接入时若暴露采样伪影，返工面 = render.rs 渲染层 + 已生产的全部素材。
  另：§1.5（:32）anchor_adjust"以逻辑尺寸入参"意味着 img.width=逻辑×d 时锚点计算要换算，
  但 §2 判据没有 anchor 矩阵（8 锚 × 8 变换，draw_image_transformed render.rs:679）测试项。
- **建议修正**：(a) 留用件入库只认"d=1 恒等"为硬闸；d>1 分支显式登记"未闭环——待真实素材
  复验"（沿 v2 blocked-by 显式化先例，resource-config-survey.md:108-110）；(b) 写明**真实
  HD 素材接入时的再验收判据**（重跑 d=1 恒等 + classic 零漂移 + 采样矩阵 + 真素材对照判读）；
  (c) §1.4 现在裁定：探针**只做最近邻**（与现实现 blit 同款，render.rs:726-736 零新算法），
  box filter 留量产件；(d) §2 判据补 anchor×transform 矩阵测试（d=2/3 各一组）。

## 攻击点 2：与 v2 配置系统的边界——density 字段归属悬空（持久化载体没写）

- **风险**：§1.7（:34）"density 载体：ArgbImage 字段 vs 显式参数——待复核定夺"只讨论
  **运行时载体**；设计件通篇没写 **持久化载体**：demo 图集生成脚本（帧像素×d 推导切片，
  :35-36）与未来 AI 放大产线都要存 density 元数据。载体不定 = v2 上线必返工。
- **反例**：对照 v2 §2.1 schema 逐字段（resource-config-survey.md:63-93）：`frame_w/frame_h`
  =逻辑值（A 档同逻辑尺寸 ⇒ 不变 ✓）、`sheet/sheet_index`/帧数/帧序/切片索引不变 ✓——
  **唯一缺口 = density/物理帧像素维度，sprite_defs/sheet_index 均无此字段**。且 v2 加载层
  "unknown-field 策略=拒载"（resource-config-survey.md:121）：探针若自造 sidecar/文件名
  约定带 density，量产接入时要么迁移（返工）要么双轨并存；探针若直接改 sprite_defs，又越界
  动了"后续另件"的 schema 主件（:8-9 边界声明）。运行时载体二选一同样悬空：改 ArgbImage
  字段（render.rs:259-264 现仅 width/height/argb）还是改 6 个消费面签名（§1.5 :30-32），
  爆炸半径差一个量级。
- **建议修正**：(a) 探针**零持久化 schema**：density 只作生成脚本参数 + 运行时字段，
  禁自造元数据格式；(b) 在 resource-config-survey.md §2.1 sprite_defs 补一行注记
  "`density`（默认 1，物理帧像素=frame_w×d）——HD 资产件预留"，一行字买断返工面；
  (c) 运行时载体现在裁定（建议 ArgbImage 字段默认 1 ⇒ d=1 恒等退化 trivially，
  消费面签名不动）。

## 攻击点 4：验收不可判——肉眼分不清"demo 画得丑"与"管线错了"

- **风险**：§2（:42）"用户人工判读 = 验收本体"；同时 §1.6（:33）"demo 面 ops 不进 L1-L3
  对拍"、visual 闸 SKIP（gates/cli.py:368-371）⇒ **管线正确性零机器判据，全靠肉眼**。
- **反例**：管线错的三种形态——切片错位（tile 拼贴重排）、几何漂移（anchor 错位）、二次
  重采样（:27 禁止的"缩回逻辑再放大"）——视觉上都表现为"糊/错位"，与"程序化绘制本身糙"
  （:48 已承认的画质上限）**同观感**。用户判读"不好看"无法归因 ⇒ 验收不可判；反之"好看"
  也不证明管线对（放大垫底区可掩盖切片错）。
- **建议修正**：验收拆两层，判据写成可执行项——
  **管线层（机器判据，不需要视觉闸）**：① ops 恒等：同场景同输入 classic vs HD 的 ops 序列
  （逻辑坐标+逻辑尺寸，render.rs:670 op 行）逐条恒等；② 直采样恒等：d==s 时像素级断言
  （目标像素集合==源像素集合，零插值——:26-27 一次映射约束的可执行形式）；③ 非素材区恒等：
  背景/HUD 白名单外像素零漂移；④ demo 图集帧数/帧序断言（:35-36 已有）+ 每帧哈希清单。
  **画质层（人工判读，只裁一维）**：判读单写成问题清单——(i) tile 边缘锐利无重影？
  (ii) tile 接缝对齐？(iii) 较 classic 清晰度可辨提升？(iv) 有无透明/色带错误？——逐项
  是/否，"整体感觉"不作数。①-④ 全绿 + 画质差 = "demo 丑但管线对"（弃件预期）；
  ①-④ 任一红 = 管线错（留用件回归）。

## 攻击点 5：排期缺失与爆炸半径——零工时账、口径不明、commit 未拆

- **风险**：设计件没有工作量估算、没有墙钟账、没有 commit 拆分（对照 v2 §5 每步明细+墙钟

- **反例**：(a) 三件合成大 commit（render.rs 改动+demo 素材+开关混提）⇒ 金样红后二分归因

  resource-config-review.md:42；爆炸半径史实 resource-config-survey.md:175-176）；
  (b) §2 判据"oracle **35/35** 帧比对"（:41）在仓库无对应口径——fixture_frames.rs 亲验
  25 个 `#[test]`、master-plan.md:118-120 "fixture_frames 21/21"与"25 测试目标 0 失败"，
  35 无出处；口径不标违 test-count-taxonomy 体例（resource-config-survey.md:183-185 引用）。
- **建议修正**：补排期与拆分表（估）：

  | 件 | 人力 | 机器墙钟 | 必过闸 |
  |---|---|---|---|
  | ① draw 路径（d=1 恒等 TDD + 采样矩阵 + anchor 矩阵） | 1.5-2 天 | gates check 2-5min×N + 金样 460s+×1-2 次 | check + trace + fixture_frames（classic 零漂移） |

  合计 **3-4.75 人日、墙钟 ≤2-3h**。commit 拆分（AGENTS.md:133 一 commit 一逻辑变更）：
  C1 `feat(core)` density draw d=1 恒等（红→绿）→ C2 `feat(core)` 采样矩阵+anchor 逻辑尺寸
  → C3 `feat(tools)` demo 图集生成（帧序断言）→ C4 `feat(shell)` --hd-assets 开关 →
  C5 `test(oracle)` scale=3 双截图对照 → C6 `docs` 复核条件吸收。动 render.rs 的 C1/C2
  必过 trace 金样 + fixture_frames 帧比对；C3-C5 不动 crates/ 判据面则 check 即可。
  "35/35"改口为**带命令的可复现口径**（跑哪条命令、数多少帧，首现标口径）。

## 攻击点 6："验证不打扰"合规——--hd-assets 开关下用户试玩的归因没写

- **风险**：§0③（:17）"可选 shell `--hd-assets` 开关"一旦交付用户，实机试玩必然发生；
  设计件未写归因口径。AGENTS.md:95-97："产品体验由用户人工试玩后反馈；**归因时不得把用户的
  操作记为验证成果**"。
- **反例**：用户开着 --hd-assets 试玩说"效果不错"，若被写进验收记录当"验证通过"⇒ 正面违反
  AGENTS §5。反过来，用户判读**无头产出的截图**（纯渲染测试/Xvfb）不属"实机/UI 验证"
  （无抢前台/发键/抓屏）⇒ 合规——这两件事必须在设计件里写清分界，否则执行者混记。
  另 :17 "纯渲染测试/Xvfb 产出"二选一未定，Xvfb 对纯渲染测试是多余依赖。
- **建议修正**：补合规注记三条：①截图产出只走无头路径，**裁定=纯渲染测试**（game-oracle
  harness，无需 Xvfb；Xvfb 仅当壳级截图兜底）；②用户试玩 --hd-assets 的反馈=产品体验
  反馈，可作画质参考记录但**不得标注为验证成果/验收证据**；③验收记录"验证"栏只填机器
  判据（攻击点 4 的 ①-④）+ 人工判读单（注明"人工判读"字样）。
