## 1. 口径（逐条指向既有引擎语义，不新立规则）

通行判定的唯一权威口径是 `crates/game-core/src/scene.rs:3251 interact_with_cell` 的 match 臂。
该函数要吃整台 `Scene`，本模块**不复制它的实现**，而是直调分类单一源
`game_core::subsystem::script_host::entity_category_with_floor(t, floor)`（
`crates/game-core/src/subsystem/script_host.rs:138`，层覆写表优先、缺省回落
`entity::render_category`），再按下列「每臂对应一句引擎行为」的映射判可走性：

| 类目 | 类型 | 引擎行为（锚） | 本模块判定 | 计数器 |
|---|---|---|---|---|
| cat1 | 1 / 2 / 3 | `consume_key_for_door` 成功 ⇒ `entity::remove`（永久开、一次扣 1） | 耗 1 钥进入，`opened` 位图 | `doors` |
| cat1 | 4 / 81 | 封印门：恒拦截 / 仅 visible 时拦截（脚本或杀敌前置） | 按**可通行** | `gates_ignored` |
| cat1 | 83 | 场景门：`try_run_scene` 命中才拦截（脚本/flag 前置） | 按**可通行** | `gates_ignored` |
| cat1 | 5 / 76 / 82 | bump 臂无 case（宝箱开启在 `applyStepCellEffects`） | 可通行 | — |
| cat1 | 6 / 7 / 8 | `stair_count += 1` ⇒ **豁免地形终审**（末尾 `if allowed && stair_count <= 0`） | 可通行；7=出口、8=入口 | `hazards`(仅6) |
| cat1 | 9 / 10 / 11 / 12 | 炼丹台 / 三昧真火墙 / 墙 / 撞击墙：`allowed=false` | **硬阻挡** | `hard_blocks` |
| cat2/4 | 26 / 27 / 28 | 踩格拾取（`2|4` 臂 + `entity::remove`） | 拾取槽，`picked` 位图 | `key_pickups` |
| cat2 | 32 | 拾取类（`sprite_defs.json` 里 **类型 32 = cat2**，不是门） | 可通行 | — |
| cat8 | 41..=78 | 撞敌可胜则开战、打不过挡住 | 按**可清** | `monsters_ignored` |
| cat16 | 77 / 78 | 告示牌/商人：触发即 `allowed=false` | **硬阻挡** | `hard_blocks` |
| cat32 | 72 / 84 / 87 | `32 => allowed = false`（联动门；72 在 f50 被覆写为 cat8 怪） | **硬阻挡** | `hard_blocks` |

- **地形**：`LevelSpec::terrain`（maplv 网格 1，行距 `w*4`、列距 2，
  `walk = tile_walkability[tile] == 1`，见 `crates/game-solver/src/solve_local.rs:1096-1108`）。
- **入场格**：该层 `ty=8`（`STAIR_DOWN`）首个槽位。**无 ty8 ⇒ `no_entry`，绝不回落
  `LevelSpec::start`**（`doors.rs::entry_and_goals` 的回落口径在此明确否决）。
- **出口**：该层全部 `ty=7`（`STAIR_UP`），到达任一即成功；**无 ty7 ⇒ `no_up_exit`**。
  判定顺序为「出口 → 入口 → 门预算 → 搜索」，故 f50（两者皆无）报 `no_up_exit`。
- **门预算**：本层门数 > 24（`u32` 掩码）⇒ `too_many_doors` **具名拒绝**，不给近似数字。
  真实 54 层最多 21 扇（f41），不触发。
- **钥匙守恒**：层内钥匙只有「开门扣 / 拾取加」两种收支 ⇒
  `held_c = entry_c + |picked∩c| − |opened∩c|` 恒等，`held` 不进状态；状态只需
  `(pos, picked, opened)`。这是**精确枚举**可行的关键（无任何状态裁剪）。
- **最小需求**：对 `(y,b,r) ∈ 0..=4³` 按 total 升序逐点**真跑** BFS，可行集对分量单调 ⇒
  已知可行向上封闭、已知不可行向下封闭双向剪枝；输出 Pareto 最小集 + 代表向量 `needed`
  （total 最小、再字典序）。分量顶到 4 则该层标 `!`（`grid_bound`，真需求可能更大）。
  网格内全不可行时用无限钥匙探针区分 `unreachable` 与 `needs_more_than_grid`。
- **钥匙向量口径 = `(y, b, r)`（黄/蓝/红）**，与 JSON `needed.yellow/blue/red` 一一对应。

## 2. 必须如实标注的假设

| # | 假设 | 方向 | 计数器 |
|---|---|---|---|
| 1 | 只算「走到任一上行梯」；不算去支线/宝箱/商店路上的钥匙 | 偏低 | — |
| 2 | 条件门 `ty83` 与封印门 `ty81/4` 的开启条件（`flags`/杀敌/脚本）不建模，按可通行 | **偏低** | `gates_ignored` |
| 3 | 怪物一律假定可清除（不扣血、不耗时） | **偏低** | `monsters_ignored` |
| 4 | 火/陷阱按引擎豁免处理（可站）；`ty6` 可通行 | 与引擎一致 | `hazards` |
| 5 | **硬阻挡按永久不可通行**（`ty9/10/11/12` + cat16 + cat32）。引擎里 `ty11/12` 可被道具或剧情消除、`ty9` 与商人可交互 | **偏高**（极端时整层 `unreachable`） | `hard_blocks` |

> 假设 5 超出任务书 4 条，单列以示区别：它不属于「钥匙需求」，而是把「非钥匙的通行前置」按最坏情况折算。

## 5. 独立第二实现复核（内部一致性判定）

`tools/keydemand_xcheck.py` 用 Python 从 `assets/raw/maplv{f}` + `sprite{f}` +

与 Rust 侧不共享任何代码：

```
cargo run -q -p game-solver --bin solver -- keydemand --out /tmp/keydemand.json
python3 tools/keydemand_xcheck.py /tmp/keydemand.json
# == xcheck: 54/54 一致, mismatch=0 ==
```

逐层比对 `status / needed / pareto / doors / key_pickups / gates_ignored / monsters_ignored /
hazards / hard_blocks` 九个字段，**54 层全等**。按 AGENTS.md §1「多路径/多实现必须给同一结果」，
这条即是本模块的等价性判据（它证明的是实现一致，不是语义正确；语义正确性由 §1/§2 的锚与假设承担）。

规模：**831 次 BFS、69 875 个状态展开、54 层总耗时 0.08 s**（debug 构建）。

  该层 **0 门 0 拾取**，`bfs_runs=1`——一次 BFS 就确认「空手可上」。3 个条件门（ty83）被忽略，
  但既不挡路也不耗钥，故对 needed 无影响。
- **f1 = `no_entry`**：**全 54 层唯一没有 `ty=8` 的层**（有 1 个上行梯在 (11,1)）。这正是「不许回落
  `level.start`」规则的现实检验点：若回落，f1 会被算出一个假数字（它的 `start` 是可走格）。
- **f51 = `no_entry`**（另一例）：有上行梯 (2,2)，但无 ty8。
- **f46 = (3,0,0)**：全图最高需求，且该层 **0 把钥匙拾取**——3 把黄必须**带入**。
  10 门 / 15 怪 / 2 硬阻挡（ty9 炼丹台 + ty32 联动门）。
- **f29 = `unreachable`**：见 §9 的机理复盘。

## 8. D 方案（needed 作为单层出层硬约束）在数据上可行吗

**在数据上可行**：Pareto 代表向量的 total 上界只有 3（f46），且 29/49 层为 `(0,0,0)`；
把 needed 当「进本层必须持有」的硬约束，不会在任何一层造成无解（单层最大 3，远小于全程黄钥
176 把的供给量级，见 `docs/findings/2026-11-17-key-flow.md`）。同时它比现有 `keys`（只数必经门）
更保守也更精确：**门的开销现在带「层内可捡多少」与「走位顺序」两件事**，
f9/f38/f41/f43 这类层还给出等价替代色。

但把它当**验收契约**用之前，四个前提必须先裁定（否则会误杀合法通关路线）：

1. 它是**下界**：条件门（假设 2）与怪物（假设 3）都按「最省」算，真实路线只可能更贵。
2. 它含一条**上界**污染：硬阻挡（假设 5）按永久不可通行，真实可被道具/剧情消除 ⇒
   有些层的 needed 虚高，极端时整层被判 `unreachable`（f29）。
3. 它只覆盖「入场→上行梯」这一段，不含支线/宝箱/商店（假设 1）。
4. f1/f51（无入口）与 f49/f50（无出口）四层**不能有约束**——它们不是「需求 0」，而是「未定义」。

**f29 的机理复盘**（为什么它 `unreachable`、且这个结论只是「按最坏假设」成立）：

```
 0 #############
 1 ###......####      S = ty8 入场 (3,11)
 2 ###g.##..####      U = ty7 上行 (8,11)   ← 目标在右下口袋
 3 ###.####W####      W = ty11 墙 (8,3)     ← 唯一竖向咽喉
 4 ###.####.####      g = ty83 场景门 (3,2)/(3,10)
 5 ###.####.####      X = ty72 cat32 联动门 (3,2)（与 ty83 同格）
 6 ###.####.####
 7 ###.####.####      左侧竖井列 x=3；右列 x=8 在 row3 被 W 截断、
 8 ###.####.####      而右下口袋与左侧在 row10-11 被地形 (x5,x6) 隔开
 9 ###.####.####
10 ###g.##..####
11 ###S.##.U####
12 #############
```

三组「消掉一个阻挡」的实验：只放开 `ty11` ⇒ 仍不通（左侧竖井被 (3,2) 的 `ty72` 卡住）；
只放开 `ty72` ⇒ 仍不通（右下口袋被 (8,3) 的墙截断）；**两者都放开 ⇒ 通**。
即 f29 的真实前置是「**联动门（cat32，需两开关/联动机制）+ 清除/绕开一堵 `ty11` 墙（道具或剧情）**」，
与钥匙无关。本模块按最坏假设把它们当永久墙，于是报 `unreachable`——**这是假设 5 的产物，不是关卡 bug**。

**另一类需要留意**：26 层 needed=0 里有几层的 0 也依赖硬阻挡（f23 硬阻挡 25、f26 硬阻挡 30、
f37 硬阻挡 37）。它们的 0 表示「按当前假设空手可上」，如果那些墙/联动门其实必须开，0 仍然成立
（开路不耗钥匙），但**绕行路线**会变——所以这 0 不是「无门可开」，而是「不开门也能上」。
