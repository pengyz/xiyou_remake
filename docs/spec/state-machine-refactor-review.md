## A1. 核心判定：「大=特例混装不是状态结构」——体积判定成立，**维护面判定不成立**

**风险**
- 判定对"代码体积在哪"是对的（普查 §3 实测：厚块 48/57/46/93 行确系特例混装），但把
  "状态机的大"整体归因于混装，**低估了转移关系本身的复杂度**：35 条边 / 40 个写点
  （scene 38 + script 2）/ 26 个消费点全部是**散点字面量**（run case 3 的 :4511/:4515、
  activate_menu_item 族 :2988-3014、m_000 各 case、interact :4962、脚本 :2342-2346……
  普查 §2 逐条锚可见）——hub 态 mode3 出边 12+ 就散在这批写点里。
- 三轻件（枚举/抽表/键码文档）**没有一件触碰边集维护**：Stage B 加一个态/一条边仍要
  人肉在 40 写点里找全、无表可对；键码（C）入注释而**边集不入文档**——选择性文档化。
- Rust 侧分派已是散点 if 链（实测 `self.game_mode == N` 形态 25+ 处，scene.rs:2857/
  4456/4474/4735/5774/5795…），"壳薄"指每态处理块体积成立，但**分派/转移字面量的
  散度**恰是第二种"大"（改动定位成本）。

**反例**
- 普查 §2 的边 #16（mode4 -7 → in_game_menu_return_mode）是**动态目标**边——边集里
  至少一族目标不是常量而是回填字段；"转移表化"即使做文档版也要表达动态边，纯 (from,to)
  表会丢这类语义——这正说明边集语义有独立复杂度，"特例混装=全部大头"覆盖不全。
- 同族前科：BUG-007 复核实证"同一 kind 两张分派表不一致"（主菜单 run tableswitch vs
  activateMenuItem）——**边/映射散点本身就是出 bug 的面**，不只是特例块。

**建议修正**
- 核心判定改双句："体积大=特例混装（解耦走件 B）；**维护大=转移边散点**（本期只文档化
  不表化，见件 D）"；
- 新增轻件 **D：边集文档化/审计**：普查 §2 转移表从一次性普查产物升为**维护义务**
  （改 game_mode 写点的 PR 须同步 §2 行；或按 fields.py 式生成器从写点扫描再生成对照）；
- 不做"转移表化"（代码层）的红线保持，但理由补全："表化=对照体断裂" ≠ "边集无成本"。

## A2. 三轻件逐件攻击

### A2-件A：枚举补全——**现状描述与实况双重不符，估算失真**

**风险**
- 方案现状句"GameMode 枚举 9 值、10 活跃态落 Unknown(i32)（type-safety 缺口+
  **match 兜底散点**）"与代码实况不符（两头都错）：
  1. **枚举没进类型路径**：`pub game_mode: i32`（scene.rs:415）——字段是裸 i32；
     `GameMode::from_raw` **全仓零调用**（仅 script.rs:403 的 Category::from_raw 是
     别的枚举）；GameMode 全仓唯一使用 = script.rs:491 `GameMode::Ending.raw()`
     （立刻转回 i32）。所谓"10 活跃态落 Unknown(i32)"在运行时**从未发生**——
     Unknown 臂是休眠码。
  2. **不存在 match 兜底散点**：`match .*game_mode` 普查 **0 处**；消费实形 =
     26 处裸 i32 `==`/`!=` 比较（scene.rs:2857/3533/4367/4424…、audio.rs:225）。
- 于是件 A 的真实工作量 ≠ "补 6 个枚举值 0.5 天"，而是**全量接线**：字段改型
  （40 写点 + 26 比较点 + 各 if 链）+ 边界点 from_raw（载档/trace 注入/夹具 preset
  的 game_mode 值）+ 序列化侧 raw()（state_dump name=value 的 gameMode 行）+
  10 新变体在每个消费点的语义映射核对。
- **match 点漏改风险的真实形态**：字段改型后裸比较是编译错（好事，编译器即完备性
  验证器）；但 `.raw()` 旁路（`self.game_mode.raw() == 15`）**编译通过且静默绕过枚举**
  ——漏改=旁路模式，不是 match 漏臂。

**反例**
- 构造：实施者按方案字面"补全枚举+match 点改全枚举"补完 enums.rs 15+ 值就算完工
  （0.5 天确实够）——运行时行为零变化、金样 55 场景全绿、type-safety 缺口**原样存在**
  （字段仍 i32）。验证武器（金样+252）对"枚举有没有真接线"零探测力。
- Unknown 兜底"形同虚设"的另一面：`from_raw` 的 `other => Unknown(other)` 在接线后
  才有意义，但**Unknown 值路径 0 测试**（tests 无 Unknown(/from_raw 注入用例）——
  "保真兜底保留=不发明语义"是主张不是实证。

**建议修正**
- 现状句改写为实况："枚举=名册层（9 变体，from_raw 未接线、Unknown 臂休眠）；
  字段 i32 + 26 处裸比较 + 40 写点"；
- 估算改口径：件 A =「枚举补 10 值 + **全量接线**（字段改型/边界 from_raw/序列化 raw()）」，
  按接线工作量重估（1-1.5 天）；
- 完备性验证=编译器（裸比较全变编译错）+ 机械普查双保险：改后 `grep game_mode == \d`
  = 0 且 `.raw()` 出现在比较侧 = 0（写检查单进 PR 判据）；
- Unknown 路径补 RED 测：`GameMode::from_raw(42)` 注入 tick 一拍 ⇒ 与今日 i32=42 行为
  逐字节一致（金样级或状态快照级）；
- "match 点"措辞废弃（不存在 match），改"比较/分派点 26 处 + 三 case 树锚"。

### A2-件B：特例抽表并入 v2——**件 B 悬空于未拍板批次，交付不可自治**

**风险**
- 件 B 全量依赖"v2 表设计批步 3"（**v2 未拍板**）——本方案的三件套实为两件半：
  B 的"完成"定义 = 别的批次完成。v2 若延期/改形，B 静默蒸发且本方案验证矩阵
  （"件 B：v2 步 3 等值单测护航"）随之失效。
- 合并执行省 460s×N 金样墙钟的理由成立，但**回归归因耦合**：同批改动=金样红时
  无法二分是 v2 表化问题还是 B 抽表问题；4 个厚块特例抽表本身就是行为面高危改动，
  与未定形的 v2 同批 = 归因成本换墙钟成本。

**反例**
- 构造：v2 决议拖两周 → 本方案结项报告写"件 B 完成（并入 v2）"而实际一行未动——
  账面完成与实际交付脱节（本仓已有"登记簿滞后于机械复算"的前科，TRIAGE 双行）。

**建议修正**
- 件 B 标注显式 `blocked-by: v2 决议`，本方案交付物 = A + C + D，B 独立挂账；
- 或件 B 自治化：按已落的 restore_rules 形态先抽 floor2/12/39 之外**无 v2 依赖**的
  特例子集（道具特例），v2 再并表；
- 合并执行的前提条件写明：v2 批内 B 改动**独立 commit**（保留二分能力），墙钟让位于
  归因。

### A2-件C：键码文档化——零代码=零验证，漂移无主

**风险**
- "26 处消费点注释锚 + 键码约定表入注释/知识库"=纯文档件：无验证器 ⇒ 写错键码语义
  （如 -5 战况/探索双义）不红；后续代码改动使注释失效时**无人报警**（注释锚漂移本仓
  已实证两次：deobf +6 行号漂移、BUG-002 grep 漏检）。
- 键码语义本身有多义性（-5 在 mode3=探索、菜单族=确认位？普查 §4"同码不同动作"）——
  文档化把多义性冻结成文字后，读者按文档修代码会引入行为差。

**反例**
- 本仓同类机制已有正例可抄：cover_matrix ARM_GAPS **锚逐条机械校验**（锚失效→⚠）——
  件 C 选了无校验的纯注释形态，是倒退。

**建议修正**
- 件 C 改为"文档 + 校验"：键码契约表随附机器可查锚（a.java:4270/4276 尾清锚 +
  26 处消费点行锚），进 cover_matrix 式校验（锚失效告警）或 PR 检查单；
- 多义键（-5/-1/-3）逐处标"态内语义"而非全局语义表；
- 指定漂移 owner（lead 或轮值）写入知识库条目。

## A3. 明确不做的三个——红线成立，但边集成本表述需补（见 A1）

**风险**
- ❌ 转移表化：理由"破坏 run/m_000 case 逐值对照性"与 execute_script_instruction
  不拆同列——**红线成立**（对照体纪律一致）；但方案把"不表化"延伸成"边集不文档化"
  （A1 已攻）。
- ❌ HSM 大拆：壳薄无收益 ✓ 成立（普查 §3 实测每态 3-7 臂×1-6 行）；
  但注意 Rust 侧分派已是散点 if 链——"大拆"对象在 Rust 里本就不存在（Java case 树
  形态在移植时已摊平），"不拆"决议对 Rust 是空集决策，表述应更精确。
- ❌ 事件 enum 统一：26 处收口=大动作小收益 ✓ 成立。

**反例**
- 对"不表化"的反例形态 = A1 的 Stage B 加态场景：新边要在 40 写点里人肉找位——
  若 D（边集文档化）不落，这个反例无解。

**建议修正**
- ❌ 列表每条补一句"不做的**代价**由谁兜"（转移表化→件 D 兜；大拆→接受散点 if 链
  现状并注明 Rust 已摊平；事件统一→键码多义由件 C 标注兜）。

## A4. 验证面：「零行为差」的武器对件 A 的真实交付无探测力

**风险**
- 金样 55 场景 + 252 测试对"枚举补全"的保护 = 0（行为本就不变），对**接线质量**
  （字段改型后的映射正确性）的保护 = 编译器 + 少量触达态的场景；未触达态（9 炼丹/
  12 记录浏览器/15 帮助/16 关于/19 商店等需特定道具/菜单路径的态）在金样覆盖里
  **可能整段空缺**——这些态的比较点改型后无行为测试背书。
- Unknown(i32) 路径 0 测试（实测 grep 0 命中）——"保真兜底"主张无实证。
- "未观测组合进枚举后 match 完备性"实况（A2 已证）：无 match；完备性=编译器拒裸比较
  + 旁路 `.raw()` 无拒——方案的验证列没写这两条。

**反例**
- 构造：`self.game_mode == 15` 改型时误写 `GameMode::About`（15/16 张冠李戴，变体名
  近形）——编译过、帮助/关于互换；金样若无 mode15/16 专属场景 ⇒ 全绿漂移。
  （方案自己都引 BUG-007 菜单错位族的教训，映射点名错误恰是同型风险。）

**建议修正**
- 验证列补三件：①Unknown 路径 RED 测（from_raw(42) 行为快照）②每变体**语义映射表**
  （变体名 ↔ a.java case 号逐行锚，如 Help=15/About=16）进方案正文（不是普查引用）；
  ③触达面清单：15 值各自被哪些场景/测试覆盖，空缺态的改型=编译器背书显式声明；
- 机械普查入 PR 判据：裸比较 0、比较侧 .raw() 0、from_raw 注入测试在位。

## A5. 方案与普查一致性抽查——数字吻合，两处措辞失准

**风险**
- 抽查结果（✓=吻合）：4 厚块 48/57/46/93 ✓（普查 §3 逐行）；35 边 ✓（§2"40 写点→
  转移边 ~35 条"）；26 处消费 ✓（§4"26 处 match（scene 20 + BootMachine 6）"）；
  40 写点 ✓（§0"scene 38 + script 2"，Rust 侧 grep `game_mode = ` 实测 40 处吻合）。
- 措辞失准 1：普查 §4 的"26 处 **match**"在 Rust 侧实为 if 链/比较（A2 已证 match=0），
  方案沿用"match"字样传递了错误形状。
- 措辞失准 2：普查 §4 标题还有"**41 写点**"（key_value 的 press 置值+清零面）——
  方案件 C 只引 26 处消费，键码契约的**写侧**（41 写点：press 覆盖式取末 + 尾清
  17+9）未入文档化范围，契约只有消费半边。

**反例**
- key_value 契约半边化：文档写"press 置值覆盖取末→消费→尾清 0"（方案 §3 有此句 ✓）
  但 41 写点不逐处锚 ⇒ "谁在何时写 key_value"的面无文档（BUG 类排查第一问）。

**建议修正**
- 件 C 范围补 key_value **写侧** 41 写点锚（press_key 覆盖 + 26 处尾清）；
- "match 点"全案改"消费/比较点"；普查 §4 标题的 match 字样一并勘误（普查维护义务）。

## 6. 总判定

**有条件通过**——三轻件方向（枚举补全/特例归位/键码契约）与三条红线（不表化/不大拆/
不统一事件）整体合理，普查数据扎实；但**件 A 的现状与估算失真（枚举未接线）**、
**件 B 悬空于未拍板批次**、**核心判定低估边集维护复杂度**三处必须修，验证面与
文档漂移守卫需补强。

**条件清单（全满足才可实施）**：
1. 核心判定改双句（体积=特例混装 / 维护=边集散点）+ 新增件 D：普查 §2 边集表转
   维护义务（PR 同步或生成器对照）（A1）。
2. 件 A 现状句按实况改写（枚举=名册层未接线、26 裸比较、from_raw 零调用）+ 估算
   改"补值+全量接线"口径 + 变体↔a.java case 号映射表入正文（A2/件A、A4）。
3. 件 A 验证补三件：Unknown 路径 RED 测、裸比较/比较侧 .raw() 机械普查入 PR 判据、
   未触达态清单显式声明（A4）。
4. 件 B 标 blocked-by: v2 决议并独立 commit（或自治化子集先行）（A2/件B）。
5. 件 C 改"文档+校验"（锚校验入 cover_matrix 式机制）+ key_value 写侧 41 写点入契约
   + 多义键逐态标注 + 漂移 owner（A2/件C、A5）。
6. ❌ 列表每条补"不做的代价由谁兜"（A3）。
