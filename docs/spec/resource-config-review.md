## ① 35-40 逻辑编辑点口径（vs 表设计 v2 的编辑点）

### ①-1 口径自称统一实则第三种单位（严重）
- **风险**：开篇沿用"一处=逻辑编辑点〔文件级〕"，但四类计数实际是**三种单位**：
  advance_frames 特例"~5 处"（行级）、dispatch_sprite_size"4 臂"（臂级）、
  图集数字"**~20 调用点**"（调用点级——明确不是文件级）。"35-40"是三种单位的和。
- **反例**：同文 §①表"已表化 5 表"按表计、"真硬编码 35-40"按点计——同一张表内单位漂移。
- **建议修正**：统一"文件级编辑点"主数 + 每类附"细目单位"列（臂/行/调用点）。

### ①-2 与表设计 v2 的点位重叠未去重（严重，直接打合批估算）
- **风险**：两普查**计了同一批点**：dispatch_sprite_size 4 臂 = v2 §1 #4"sprite 图集/动画
  dispatch 分派"；advance_frames 特例 = v2 #4 的"动画"侧；render_category 10 臂 = v2
  EnemyDef **缺字段**（dispatch review-B1 点名的缺口，本调研 §④ 补上了）；cat8 渲染臂 93 行
  两边都提（v2 #10 / 本调研 §④）。**同一次重构在两份估算里各计一次工时**。
- **反例**：本调研 §3 已做"一事实一宿主"裁定（真值归 sprite_defs、enemy_defs 只存外键）——
  **数据归属裁定做了，工时归属没做**：步 3"消费替换 2-3 天"与 v2 步 3"消费替换 1-2 天"
  覆盖同一函数族（scene.rs paint/interact、entity.rs dispatch）。
- **建议修正**：出**编辑点合并账本**（点 × 宿主 × 归属普查 × 工时唯一归属），合批估算按
  去重后点数重算；v2 的 4-5 天与本调研 6.5-7.5 天里互相重复的部分显式划拨。

## ② 6.5-7.5 天估算依据 + 墙钟叠加

### ②-1 估算无依据：无每步明细、无机器墙钟、无风险余量（严重）
- **风险**：五步天数（2/1/2-3/1/0.5）没有拆解依据；**步 3"每点一闸"与 2-3 天不相容**——
  ~35-40 点里若每点过一次 45 场景金样（单场景实测 460s 级，全量 45 场景小时级/次），
  仅机器墙钟就是 60-120 小时；若"闸=等值单测而非全量金样"，口径必须写明。
- **反例**：v2 同款估算已被 dispatch review-D3 判"无依据"（4 点×RED→GREEN×回归墙钟未计）
  ——本调研复制了同病。
- **建议修正**：每步给"人力天 + 机器墙钟"双列；步 3 闸级定义（单测级/金样级/抽样级）；
  加 ≥20% 风险余量（表设计批实测：d6a9cef 一次插入就揪出两处 harness 漂移）。

### ②-2 "合批 13-15 天"大于两线分计之和——省时主张被自家数字证伪（严重）
- **风险**：§5 排期称"表设计+资源配置合批（~13-15 天）…共享保真表基建+**一次金样墙钟**"。
  但两普查**自家估算之和 = 4-5 + 6.5-7.5 = 10.5-12.5 天**——合批反而**多 2.5-4 天**，
  "共享墙钟省钱"在哪里？若 13-15 已含协调开销，那主张应改为"合批多花 2-4 天买基建共享"。
- **反例**：lead 侧对账口径（v2 修订后 9-10 天 + 本调研 6.5-7.5 + 状态机 2-3 + 分辨率 7-11）
  串行总量 = **24.5-31.5 天**；本调研路线（13-15 + 2-3 + 7-11）= 22.5-29 天——差距全部押在
  "合批共享"这一未量化假设上，且金样墙钟是**串行资源**（同机跑闸时人力闲、多人并行时抢机器）。
- **建议修正**：要么把"共享墙钟节省"折算成数字（省几次全量回归×每次小时数），
  要么改口"合批=多花 2-4 天换基建一次成型"；墙钟预算单列（见 ②-1）。

## ③ 合批排期风险（v2+资源合批 = 一次大爆炸半径）

### ③-1 大 diff 金样红的二分归因成本未计（严重）
- **风险**：v2 步 3（trait/钩子/respawn/渲染消费替换）与本调研步 3（advance_frames/
  dispatch/图集/category）**同触 scene.rs paint/interact、entity.rs dispatch**；合批一次
  回归红了，二分要在两批叠加的 diff 里找因——归因成本随 diff 大小指数上升。
- **反例（仓库史实）**：本仓近 48 小时的重构全部是小步"金样零漂移" commit
  （313375b SoA→struct 427 站点 / 76cb6c2 六写点收口 / 5894bfb 文件合流 /
  8a455dd ScriptOp 拆分 / efc6fe5 特例批——每步独立闸零漂移）；d6a9cef 正是**因为 diff 小**
  才当场揪出两处 harness 真漂移。大爆炸半径没有成功先例，反有字高事故（3423db7，
  靠用户试玩才发现）的失败先例。
- **建议修正**：合批只共享**基建**（evidence 列/两份制/校验器框架），**不共享爆炸半径**——
  按子面拆 commit 序列（每 commit 一闸）；或直接分批（v2 先行→资源跟进），回归触发
  时机可以合排，diff 归因边界不可合。

## ④ 零改码验收判据（"加一个假想敌人"演练）

### ④-1 验收标准未定义（严重）
- **风险**：步 5"0.5 天：加一个假想新敌人=纯表+资源，验证零 Rust 改动"——谁定假想敌人的
  规格？怎样算过？"零 Rust 改动"（git diff --stat 空）只是**必要条件**：新敌人还要
  **渲染对、数值对、行为对**。而两份制下 mod 表资源**不进金样**（§2.3）——新敌人的正确性
  用什么验证？独立基线？断言测试？**验证通道未定义**。
- **反例**：假想敌人若挂 DSL（script_ref），行为正确性连等值单测都没有对照物（新行为无
  "旧值"）——0.5 天只够"加行不炸"。
- **建议修正**：验收判据三件套并由用户/lead 裁定留痕：
  (a) 零 Rust diff 清单（crates/** 无改动）；
  (b) 新敌人性质断言（帧渲染像素断言/战斗数值/掉落表各一条）；
  (c) 行为链断言（若挂 script_ref，脚本执行 trace 断言）。

### ④-2 失败面设计缺失（严重）
- **风险**：资源文件格式错 / JSON schema 违规 / 外键断链 / 型号域溢出（89 项外）/
  帧序越界——五类坏输入的失败模式未设计：L1 golden 只锁"解析正确"，**用户 mod 坏文件**
  是拒载？降级？game-data 解析 panic？游戏启动炸？错误面没有归属（gates 拦 vs 运行期报）。
- **反例**：BUG-012 的教训直接适用——运行期炸的失败面（脚本重入环）排查成本极高；
  坏 mod 资源是**用户可触达**的运行期炸，比脚本坑更常见。
- **建议修正**：失败面测试进验收（坏 JSON/坏外键/域溢出/帧序越界各一例，断言错误信息
  与拒载行为）；mod 加载路径的错误=结构化 Result + 壳层提示，禁 panic（确定性红线相邻）。

## ⑤ mod 骨架（1 天）范围

### ⑤-1 1 天装不下五件事（中）
- **风险**："校验器进 gates + mod 表骨架 | 1 天"——骨架至少含：①用户资源加载路径
  （jar 内 vs 运行目录 mod/？）②目录/命名约定 ③mod 表与保真表**叠放优先级/冲突裁决**
  （同 type_id 两表都有的行谁赢？字段级还是行级覆盖？）④坏 mod 失败面（④-2）⑤确定性
  边界归属（game-core 禁 IO ⇒ 加载必须在壳层/platform——survey 未写归属）。
- **反例**：dispatch review-B6 的 script_ref 触发语义未定义是同型病——"骨架 1 天"默认
  这些设计问题不存在。
- **建议修正**：mod 骨架单列设计清单（上述五件）+ 工时重估（设计 1 天 + 实现 1-2 天）；
  叠放语义（行级 or 字段级覆盖）是 schema 问题，必须在步 1 定稿前裁定。

## 判定

**有条件通过** ——方案层（schema/两份制/一事实一宿主/分工边界）质量好；但**排期层三处
不达标**：编辑点口径与 v2 重叠未去重、估算无依据且合批主张与自家数字矛盾、验收判据与
mod 骨架范围未定义。**条件清单**（全部满足方可开工）：

1. **编辑点合并账本**：与表设计 v2 逐点去重（重叠：dispatch_sprite_size/advance_frames/
   render_category/cat8 臂），工时唯一归属；口径统一"文件级 + 细目单位分列"；
2. **估算补依据**：每步"人力天+机器墙钟"双列、步 3 闸级定义（单测/金样/抽样）、≥20% 余量；
   "合批 13-15 天"给出节省折算或改口"多花 2-4 天买基建一次成型"；
3. **排期结构**：合批只共享基建不共享爆炸半径——按子面拆 commit 序列每 commit 一闸
   （仓库小步体例史实为据）；或 v2/资源分批；
4. **零改码验收判据三件套**（零 Rust diff 清单 + 新敌人性质断言 + script_ref 行为链断言）
   + 失败面测试（坏 JSON/坏外键/域溢出/帧序越界），判据定义权 lead/用户裁定留痕；
5. **mod 骨架五件套设计**（加载路径/目录约定/叠放优先级/坏 mod 失败面/确定性归属）
   单列 + 工时重估；叠放语义（行级 vs 字段级）在 schema 定稿前裁定；
6. **金样场景数更正 45/45**（9620ed2）——本调研"金样 55 场景"是同口径病**第四次出现**
   （dispatch review-D2、viewport review-①、本 ② 参照）；建议在某处钉死全局口径注记。
