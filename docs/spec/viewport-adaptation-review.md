## V1. 金样两档策略：两档 ratchet 无一致性契约，且"分辨率无关共用"与倾印内容矛盾

**风险**
- **"状态向量/脚本行为断言分辨率无关共用"（§2）是未验证假设，且被倾印内容直接证伪**：
  state_dump.rs 明明倾印 **视口耦合字段**——`cameraPixelX/Y`（cam_x/cam_y，:94-95）、
  `viewWidthPx`（view_w，:96）、playerPixelX/Y（:88-89）。同一场景 480×640 跑出的
  `viewWidthPx=480`、cam 值随居中公式 `((view-32)>>1)-offset` 变——**状态向量逐字节
  不可共用**。"共用"若成立，必须显式声明共享字段子集（剔除视口/相机字段）——调研没有。
- **脚本 tick 节拍经相机门分辨率耦合**：dialogPhase=4（AwaitCamera）等
  `cameraAtTarget` 收敛，而收敛距离=f(视口尺寸)（ease 目标 `((view-32)>>1)-offset`、
  ease 步长固定）⇒ **同一脚本在不同分辨率下事件 tick 序移位**。"脚本行为断言共用"
  对穿过相机门的场景不成立；夹具 tick 锚（T302/T405 类）在变分辨率下必然漂移。
- **两档 ratchet 一致性无人负责**：240 档=state-dump 逐字节（有 Java A 侧锚）、
  视口档=新 golden 帧（生成后冻结，**无任何外部锚**）——两档之间没有交叉校验器。
  逻辑 bug 若只在非 240 尺寸显形（如居中取整、裁剪边界），240 档全绿、视口档把 bug
  冻成基线。
- **工具链 240 锚定**：frames_fixture.py 头注自证——夹具期望帧=**Java 参照帧**、
  cover_matrix 以 `A-<stem>` 注释头认领并与 method_reach frame_chain 逐字节比对。
  第二档 golden 无 `A-<stem>` 可认领（Java 侧不存在 480×640 运行），现有验证链
  （fixture↔snapshot）**认领不到视口档**——调研未提工具链适配。

**反例**
- 构造：Phase 2b 把弹窗居中公式改为 `self.width - w >> 1`（语义正确方向）但取整用
  `(width - w) / 2`（奇宽下差 1px）——240 档 240-w 恒偶、金样绿；480/720 档亦偶、
  视口基线生成即冻结该行为；未来 Phase 3 奇宽分辨率进场才炸，而那时基线已"冻结"无锚。
- 构造：相机 ease 在 480 宽下收敛多花 3 tick ⇒ dialogPhase 4 早退/晚退 ⇒ 脚本事件序
  相对 tick 锚移位 ⇒ 若视口档基线用"逐 tick 帧"冻结，把**时序差**冻进基线还判"一致"。

**建议修正**
- 两档契约显式化：①**跨档状态等价测试**（同场景 240/480 双跑，断言共享字段子集
  逐字节相等——子集清单入正文，剔除 cam_x/cam_y/view_w/view_h 及其派生）；
  ②相机门时序声明（"穿 AwaitCamera 的脚本 tick 锚与分辨率相关"——这类场景在视口档
  只断言事件序不断言 tick 号，或按 ease 收敛公式归一化时轴）；
  ③视口基线生成**前置条件** = V2 屏外语义逐项 disposition 落地（见下），生成器拒绝
  在 disposition 未齐时产基线；
- 工具链适配列为 Phase 2c 交付物：frames_fixture/cover_matrix/method_reach 认领
  视口档的机制（如 `# viewport: WxH` 头 + 独立 frame_chain 命名空间）；
- "分辨率无关共用"改为"**分辨率无关字段子集共用**（清单化）+ 帧/tick 锚 240 专属"。

## V2. 屏外语义分叉：「已知 ≥3 处」是计数不是清单，分叉类别 ≥5 类无 disposition

**风险**
- 调研 §2 只给"逐条考证清单（已知 ≥3 处）"并列三例（logo x=240 / 弹窗 x=240 /
  PARALLAX_WRAP=-154）——**这是计数留白不是清单**；实测分叉类别远不止：
  1. **屏外起点/锚定**：logo 起点 x=240（logo_anim）、弹窗 kind4 `x=240` 右缘锚
     （popup.rs:65 `self.x[w] = 240`）；
  2. **回绕阈值**：PARALLAX_WRAP=-154（layout.rs:116，周期 155）——背景卷动周期与
     画布宽的语义关系（宽画布下 -154 外仍可见=回绕视觉断点）；
  3. **全屏覆盖操作**：换层 wipe `40×30 格 8px`（a.java:3217-3224=恰好铺满 240×320）、
     logo 时间线 `setClip(0,0,240,320)/fillRect(0,0,240,320)` 期望串（logo_anim.rs:516-535
     10+ 处、paint.rs:879）、dim/遮罩类；
  4. **画布宽居中公式**：a.java `240 - … >> 1` 形态 **19 处**（弹窗/说明框/存档槽
     `240 - slotListWidth >> 1` :9171、`240 - f_int_75 - 22 >> 1` :2697 等）——
     扩画布后公式引用 240 还是 width = 每处一次语义决定；
  5. **固定布局点**：对白 layout `layoutWrappedText(…, 129, …)`（:8246）/`209`（:3047）、
     showOverlayMessage 文本 y=234/240/212（:3036-3039）——画布宽相关排版。
- **保真破坏的真反例形态**：原版"240 边界=语义边界"——logo 从 x=240 滑入是**动画时序**，
  扩画布后若改"画布外起点"，滑入时长=f(width) 变（行为差）；若不改，logo 起手就在
  画面中央（也是行为差）。**两个方向都分叉**——每处必须做语义 disposition 并把选择
  记为扩展面契约，调研的"逐条考证"没有给出逐条形态与归属。

**反例**
- 换层 wipe：40×30×8px 在 480×640 画布只盖 1/4 面积——若"修"成按 width 迭代，
  240×320 帧夹具对拍不受影响（240 处行为同），视口档冻结的却是"1/4 遮罩"或"全屏遮罩"
  之一——哪个是意图没有裁定就进基线（V1 的冻结风险与本条叠加）。
- 弹窗 kind4 x=240：240 画布=右缘贴边；480 画布=画面中央浮窗。改 width-w=右缘（观感
  连续）还是保 240=（保真位置语义）？调研未裁。

**建议修正**
- §2 的"≥3 处"升级为**逐条 disposition 清单**（上列 5 类全数入册，每条：原版语义/
  扩展面处置〔随宽/钉 240/离屏判定改画布外〕/验证归属〔240 帧夹具 or 视口基线 or
  跨档等价〕）；
- "屏外判定"处置原则先裁定（建议：**离屏检测改画布外、离屏起点/锚定钉 240 语义并
  文档化分叉**——两类分开，不要一句话"改画布外"带过）；
- wipe/dim/setClip 类全屏操作单列（它们不是"屏外"问题，是**覆盖域**问题）。

## V3. 逻辑坐标 vs 视口坐标分离：边界案例（脚本坐标/帧夹具锚）归属未清

**风险**
- 脚本坐标面：格坐标（MOV_72_3_7_1_8）与像素（<<5）确实分辨率无关 ✓；但脚本驱动的
  **排版/相机**不是——openDialogPage 固定 x=129/209、SEE/ROS 相机目标含视口项、
  CES 相机居中（a.java:8399 `cameraX = (viewWidthPx - 32 >> 1) - cameraPixelX`）——
  "脚本坐标=逻辑系"的边界应精确到"格坐标无关；脚本引发的渲染/相机行为视口耦合"。
- 帧夹具锚：frames.txt 逐 tick 帧 sha = **240×320 渲染产物**；Phase 2a（const→Layout）
  若夹具 harness 走"环境默认视口"而非显式 `Layout(240,320)` 注入，默认值一漂全部
  夹具红或被重新生成洗白（frames_fixture 重生成=Java 参照帧重新嵌入——240 档有 A 侧
  可重生成，但"重生成"动作本身就能把 Layout 误值洗成新期望）。
- 时序锚：V1 已述 tick 锚经相机门耦合——夹具"T302 FLD 跳变"类断言在视口档不可移植。

**反例**
- 构造：Phase 2a 给 fixture 测试默认 `Layout::current()`（含全局可变默认）——某测试
  先跑 480 场景污染全局默认 → 后续 240 夹具红，且**非确定**（测试排序敏感）；
  "金样全闸零差"在单测排序下不稳。
- 构造：frames_fixture 重生成时 Java 参照帧仍是 240（A 侧永远 240），而 Rust 侧
  渲染跑在被污染的默认视口 → 期望帧=240、实际帧=480 尺寸 → 红；有人"修"测试传参
  后一切绿，但若当时顺手改了期望帧生成脚本的裁剪，A 侧锚被静默削弱。

**建议修正**
- 夹具 harness 显式注入 `Layout(240,320)`（构造参数，禁全局默认态）+ 单测隔离性
  断言（无共享可变全局）；
- 帧夹具重生成协议写红线：重生成仅允许"Java 参照帧重新提取"（A 侧字节不变），
  期望帧 sha 变 = 立即停（frames_fixture 头注的源 trace sha256 已有此精神，写成
  流程判据）；
- "脚本坐标无关"表述精确化（格坐标无关 / 脚本渲染-相机行为耦合两分）。

## V4. 对照锚完整性：「对照性可保」无机制，取值来源改≠值中立的边界

**风险**
- §1②断言"常量值不动、只改引用方式，对照性可保"——**可保是主张**：102 const 升
  `Layout` 结构字段/求值函数后，a.java 行号对照锚的**载体**变了（layout.rs const 行 →
  struct impl/求值表达式），锚若不随迁就漂（本仓锚漂移前科：deobf +6 平移两次修正、
  TRIAGE 双行登记滞后）；
- "取值来源改"（const 字面 → 运行时字段求值）在整数除法/移位上**值中立不成立**：
  `240 - w >> 1` 与 `(width - w) >> 1` 在 width=240 等值；width 换档后取整方向由
  实现选择——240 金样测不到（V1 同根）；`CENTER_X = SCREEN_W/2` 编译期常量 vs
  运行期求值，i32 语义一致 ✓ 但溢出/推导链重排（`A-B>>1` vs `A>>1-B>>1`）会变值；
- 渲染几何的对照性在**散点归位**（57 调用行收进 Layout）后：归位=代码搬家，
  搬家 commit 若不含锚随迁表，对照体审计（如 coverage-matrix 的行锚校验）会失配。

**反例**
- `GAME_VIEW_H=252`（f_int_59 派生、头注自警"扩视口需逐条考证"）——它**不是
  SCREEN_H 派生**，Layout 契约化时若按"派生常量随画布联动"的统一规则处理 252，
  直接改错语义（252 是游戏区高度的原版实测值，不是 320-68 之类干净公式）——
  调研①已警但方案层（§3.1"派生 const 随 SCREEN_W 联动设计已含契约雏形"）把它
  归并进了"联动设计"，两处口径打架。

**建议修正**
- 每个常量入 Layout 时**锚随迁**：字段注释保留 a.java 行号锚 + 对照表（Rust 值↔a.java
  锚↔公式形态）随 commit 更新；对照锚进 cover_matrix 式机械校验（锚失效告警）；
- "值中立"边界单列：移位/除法表达式**原式逐字搬**（禁重排推导链），取整方向以
  240 金样 + 跨档等价测试双钉；
- GAME_VIEW_H=252 例外显式化：标"实测常量（非派生）"，不随画布联动，扩视口时
  按考证结论单独处理（调研④的考证义务与 §3.1 的契约化口径合并对齐）。

## 5. 总判定

**有条件通过**——五类普查扎实（实测计数/分期合理/Phase 1 已达的判断属实/逻辑系与
视口系分离的**方向**正确），但**保真验证面四洞**：两档 ratchet 无一致性契约且
"分辨率无关共用"被倾印内容证伪（V1）、屏外分叉是计数不是清单（V2）、帧夹具/时序锚
归属未清且重生成协议缺红线（V3）、对照锚"可保"无机制（V4）。任一落地都会出现
"基线绿但行为漂移/分叉被冻成期望"。

**条件清单（全满足才可进 Phase 2）**：
1. 跨档等价契约：共享字段子集清单 + 双跑状态等价测试 + 相机门时序声明（V1）；
2. 视口基线生成前置 = 屏外分叉逐条 disposition 落地；生成器拒绝未齐生成；冻结协议
   写明"生成后仅侦测变更不证正确"（V1/V2）；
3. 屏外分叉 5 类全数入册逐条 disposition（离屏检测 vs 起点/锚定分开裁定；全屏覆盖
   操作单列）（V2）；
4. 夹具 harness 显式注入 Layout(240,320) 禁全局默认；帧夹具重生成红线（A 侧字节不变
   才许重生成）（V3）；
5. 对照锚随迁机制 + 机械校验；公式原式逐字搬；GAME_VIEW_H=252 例外显式化（V4）；
6. 工具链（frames_fixture/cover_matrix/method_reach）视口档认领机制入 Phase 2c
   交付物（V1）。
